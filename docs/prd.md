# NexusSklad PRD

Дата: 1 марта 2026
Статус: draft product requirements document

## 1. О продукте

`NexusSklad` — mobile-first система складского учета для малого бизнеса, стартующая с рынка Дербента.

Продукт помогает владельцам и сотрудникам:

- вести учет товаров;
- отслеживать остатки;
- фиксировать приходы и расходы;
- проводить инвентаризацию;
- контролировать движения и действия сотрудников;
- работать без тяжелой ERP.

## 2. Проблема

Малый бизнес часто ведет учет через:

- Excel;
- бумагу;
- WhatsApp;
- устные договоренности;
- неструктурированные заметки.

Из-за этого возникают проблемы:

- нет точного понимания остатков;
- теряются товары;
- возникают ошибки в приходах и расходах;
- владелец не видит реальную картину;
- сотрудники работают без прозрачного контроля;
- инвентаризация превращается в хаос.

## 3. Целевая аудитория

### Основная

- владельцы складов;
- владельцы оптовых точек;
- управляющие;
- завсклады;
- сотрудники склада.

### География старта

- Дербент

### Приоритетные ниши

- стройматериалы;
- хозтовары и бытовая химия;
- оптовые точки;
- автозапчасти.

## 4. Ценность продукта

`NexusSklad` позволяет запустить складской учет за 1 день, работать со смартфона и контролировать остатки и движения без перегруженных систем.

## 5. Цели продукта

### Для бизнеса

- получить первых пилотных клиентов;
- доказать, что продукт реально экономит время и снижает хаос;
- создать локально сильный SaaS-продукт.

### Для пользователя

- видеть остатки в реальном времени;
- быстро оформлять приход и расход;
- легко искать товары;
- проводить инвентаризацию без боли;
- понимать, кто что сделал.

## 6. Успех продукта

Метрики успеха на первом этапе:

- 3-5 пилотных клиентов;
- не менее 3 активных операций в неделю у каждого пилота;
- повторное использование после первой недели;
- реальная ежедневная польза для владельца;
- подтверждение готовности платить.

## 7. Scope MVP 0.1

### Входит

- регистрация компании;
- вход пользователей;
- роли `owner`, `manager`, `staff`;
- товары;
- категории;
- остатки;
- приход;
- расход;
- история движений;
- поиск товара.

### Не входит

- бухгалтерия;
- 1С-интеграция;
- кассовый контур;
- маркетплейсы;
- сложные отчеты;
- мультискладовая enterprise-логика;
- продвинутые интеграции.

## 8. Scope MVP 0.2

- инвентаризация;
- журнал действий;
- отчет владельца;
- низкий остаток;
- Telegram-уведомления.

## 9. Функциональные требования

### 9.1 Авторизация

Пользователь должен иметь возможность:

- зарегистрировать компанию;
- войти по телефону/email;
- получить доступ в зависимости от роли.

### 9.2 Товары

Пользователь должен иметь возможность:

- создавать товар;
- редактировать товар;
- удалять товар;
- видеть остаток;
- искать товар.

### 9.3 Категории

Пользователь должен иметь возможность:

- создавать категории;
- редактировать категории;
- прикреплять товар к категории.

### 9.4 Приход

Пользователь должен иметь возможность:

- выбрать товар;
- указать количество;
- сохранить операцию;
- обновить остаток.

### 9.5 Расход

Пользователь должен иметь возможность:

- выбрать товар;
- указать количество;
- списать товар;
- зафиксировать операцию.

### 9.6 История движений

Пользователь должен видеть:

- список операций;
- дату;
- тип движения;
- количество;
- ответственного сотрудника.

### 9.7 Поиск

Пользователь должен иметь возможность искать:

- по названию;
- по SKU;
- по штрихкоду позже.

### 9.8 Инвентаризация (MVP 0.2)

Пользователь должен иметь возможность:

- начать инвентаризацию;
- вводить фактические остатки;
- видеть расхождения;
- завершить инвентаризацию.

### 9.9 Роли

`owner`

- полный доступ;
- видит отчеты;
- управляет ролями.

`manager`

- управляет товарами и операциями;
- видит движения;
- не управляет всем аккаунтом.

`staff`

- выполняет приход/расход;
- видит доступные товары;
- не управляет ролями и системой.

## 10. Нефункциональные требования

- приложение должно быть понятным без долгого обучения;
- основные операции должны быть доступны с телефона;
- ключевые действия должны выполняться быстро;
- интерфейс не должен быть перегружен;
- все операции с остатками должны быть надежными;
- система должна быть готова к future offline mode.

## 11. Основные риски

1. Слишком широкий scope.
2. Слишком ранняя сложная архитектура.
3. Отсутствие узкого сегмента на старте.
4. Слабый онбординг клиентов.
5. Попытка конкурировать с 1С на поле 1С.

## 12. Definition of Done для MVP 0.1

MVP 0.1 считается готовым, если:

- компания может зарегистрироваться;
- можно создать категории и товары;
- можно сделать приход и расход;
- остатки пересчитываются корректно;
- история движений сохраняется;
- поиск работает;
- роли разграничены;
- пилотный клиент может реально использовать систему в ежедневной работе.
